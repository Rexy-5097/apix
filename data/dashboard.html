APIx — Airfare Index Engine

A frozen-specification airfare index engine with a real-market evidence pipeline, built against MoSPI problem statement 26056. We have collected and audited the complete seven-bucket advance-purchase panel for DEL–BOM under a fixed collection protocol. The engine is implemented and tested, but we deliberately do not publish a market index yet, because the longitudinal evidence the methodology requires does not exist.

Observed 35 real observations 7/7 frozen APW buckets · 5 departure bands · DEL-BOM · IndiGo 6E · collected 2026-09-12
Engine Implemented & tested APIx-L: Jevons elementary → Young / Modified Laspeyres, verified end to end over 14 consecutive publication dates of a controlled synthetic test fixture. No real longitudinal index calculation has been executed. No ML in the index path. APIx-TPD is specified (§M) but not implemented.
Index PENDING Frozen methodology requires matched t / t−7 evidence: §C.1 I(c,t) = I(c,t−7)·J(c,t). 1 collection wave held ⇒ 0 matched pairs. Unlock 2026-09-19.
No APIx market index value appears anywhere on this page. The advance-purchase profile below is descriptive cross-sectional evidence. It is NOT a longitudinal airfare price index, and no figure on this page should be read as airfare inflation.

Lead time is confounded with travel date

Advance-purchase buckets are not interchangeable time observations. In this panel lead time is confounded with travel date / day-of-week, so the APW profile is descriptive and is not an inflation measure.

This profile does not isolate the effect of advance purchase. Advance-purchase buckets are not interchangeable time observations. Separating lead time from travel date needs the same cell observed at two collection dates seven days apart — which is exactly what the matched t / t−7 design does, and exactly what one collection wave cannot provide.

How far the real observations actually travel through the frozen code — reconstructed from this contract and run stage by stage through the frozen functions named below. Real market observations pass through APIx's admissibility, banding, key construction, deduplication and source-precedence stages. The pipeline stops at the longitudinal Jevons step because the required t-7 observation does not yet exist. Only the named stages are exercised; the elementary layer is not exercised as a whole.

DEGENERATEthe code executes, but the single-wave / single-source panel supplies too little variation for the property to be established.
PENDINGthe frozen methodology requires evidence that does not exist yet.
BLOCKEDrefused by a publication guard, by design.

Statistical methodology

raw observation→ admissibility §A.6→ dedup §D.4→ clean panel→ Jevons §D.2→ Young / Mod. Laspeyres §F→ APIx

Green steps run on today's data. Amber steps are implemented and invariant-tested but have no input yet, because every one of them consumes a price relative, and a relative needs two collection waves. Green here means “runs on today's data”, which is the same thing section 09 calls EXERCISED — not “validated”. Three of those stages are degenerate on a single wave; section 09 names which.

§D.2Jevons elementary aggregation. Geometric mean of matched price relatives within a cell, computed in logs — the log form is normative, not a numerical convenience. Matches MoSPI's own elementary aggregator for CPI.
§FYoung / Modified Laspeyres. Weighted aggregation above the elementary level. Route weights are specified to use DGCA city-pair passenger volumes; that source is not yet secured, and with one route no route weighting is exercised.
§MAPIx-TPD — SPECIFIED, NOT IMPLEMENTED. A quote-level Time Product Dummy hedonic regression, designed as a parallel estimator never chained into APIx-L. The specification exists; the estimator is not implemented (src/apix/statistics/tpd/ is an empty package). The design intent — publishing the gap between the two estimators — is a future deliverable, not a present one.
§NUncertainty — NOT IMPLEMENTED. No bootstrap or confidence-interval estimator exists (src/apix/statistics/uncertainty/ is an empty package), and no confidence interval is reported anywhere in APIx. Beyond the missing code, the current collection design does not record the admissible-flight universe per band, so it does not yet carry the sampling-design information a conventional uncertainty estimator would need. Dispersion is reported instead, which assumes nothing.

The 30-day back-test the problem statement asks for is not performed and not simulated. This is the route to it.

Anticipated questions

Why don't you show an index value? Because the locked longitudinal specification requires matched observations at t and t−7. One collection wave cannot produce a legitimate time-series relative, and changing the formula to manufacture one is the single thing the frozen methodology forbids.
Then what have you actually demonstrated? A complete real-data path: compliant collection, extraction verified against source evidence, canonicalisation, deduplication, admissibility, hash-addressed provenance and an auditable exclusion trail — plus an index engine that is implemented and invariant-tested and is waiting on input, not on code.
Why only IndiGo and DEL–BOM? Compliance, not convenience. Of 14 sources audited, IndiGo is the only one carrying an affirmative, quoted permission for the collection mode used. DEL–BOM is India's densest domestic pair. The architecture is route- and carrier-agnostic throughout.
Why not just use MoSPI's published airfare index? It is a monthly All-India reference index, not route-level raw fare observations. It is the validation target, and it is exactly what this project exists to complement at higher frequency and finer granularity.
Why Saver rather than the cheapest visible fare? The frozen contract standardises the fare family so a hand-baggage-only Lite fare is never pooled with a checked-baggage product. Canonical fare class is derived from entitlements, never from the marketing label.
Why exclude later, cheaper flights in the same band? The protocol takes the earliest qualifying flight in each departure band. Selecting by price would make the index measure its own selection rule, and no downstream test could detect or undo that.
Why is T+60 so much higher? It is an observed cross-sectional difference, not a causal estimate. Each APW sits on a different travel date, so seasonality and date effects are confounded with lead time. The post-Diwali hypothesis is plausible and untested.
What happens after the hackathon? Run the same collection longitudinally from 2026-09-19, expand routes and carriers, bring in DGCA weights, then perform the 30-day validation and begin regular index computation.
